# Refresh token: логика в PawPal

## Зачем два токена

Обычно выдают **два токена**:

| | **Access token** (JWT) | **Refresh token** |
|---|------------------------|-------------------|
| **Срок жизни** | Короткий (в проекте: **15 минут**) | Длинный (в проекте: **7 дней**) |
| **Где хранится на клиенте** | Memory / заголовок `Authorization` | HttpOnly cookie или безопасное хранилище |
| **Назначение** | Вызывать API; быстро протухает | Не посылать на каждый запрос; только обновить пару токенов |

**Идея:** access часто истекает или может утекнуть — ущерб ограничен по времени. Refresh живёт дольше, но используется редко (один эндпоинт), его можно **отозвать** при выходе или компрометации.

---

## Как это реализовано в коде

Реализация: `internal/service/auth_service.go`, хранение: `internal/repo/refresh_token_postgres.go`, HTTP: `internal/handler/auth_handler.go`.

### Логин (`Login`)

1. Проверяются email и пароль (`bcrypt`).
2. Генерируется **JWT** (`generateAccessToken`) с полями `sub`, `email`, `exp` (**~15 минут**).
3. Генерируется случайная строка (**32 байта → hex**) — это **refresh token** (`generateRandomToken`).
4. Refresh сохраняется в таблицу `refresh_tokens`: `user_id`, `token`, `expires_at` (**+7 дней**).
5. Клиенту возвращается JSON с полями `access_token` и `refresh_token` (`AuthTokens`).

### Обновление (`Refresh`)

1. Клиент отправляет в теле запроса `refresh_token`.
2. `GetValid` ищет в БД запись: токен совпадает, **`revoked_at IS NULL`**, **`expires_at > now()`**.
3. По `user_id` загружается пользователь.
4. Выдаётся **новый** access JWT.
5. **Rotation:** старый refresh **отзывается** (`Revoke`), создаётся **новый** refresh на те же 7 дней.
6. Клиент получает новую пару `access_token` + `refresh_token`.

Так реализована **ротация refresh-токенов**: после успешного обновления старый refresh больше не принимается — украденная копия «старого» токена становится бесполезной после одного легитимного refresh.

### Logout

- Для переданного `refresh_token` вызывается `Revoke` — в БД выставляется `revoked_at`, токен больше не проходит `GetValid`.

---

## Зачем хранить refresh в БД

Refresh — случайная строка, не «самодостаточный» долгоживущий JWT без состояния: сервер **помнит**, какой токен выдан, **не отозван ли он** и **не истёк ли**. Это позволяет **инвалидировать** конкретный токен при logout и вести учёт при ротации.

---

## Типичный сценарий для клиента

1. **Логин** → сохранить `access_token` и `refresh_token`.
2. **Запросы к API** → `Authorization: Bearer <access_token>`.
3. Если access истёк (**401**) → **POST** с телом `{ "refresh_token": "..." }` → получить новую пару, повторить запрос.
4. **Выход** → **POST** logout с `refresh_token` → refresh инвалидируется на сервере.

---

## Связанные эндпоинты (handler)

- Логин — выдача пары токенов.
- Refresh — обмен refresh на новую пару (с ротацией).
- Logout — отзыв refresh в БД.
